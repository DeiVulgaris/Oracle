# 🏛️ Oracle: Flip & Resonance (v3.0 — Freemium SaaS)

> **Oracle gives the first answer. Your reaction gives the second.**

## 1. Product Concept

**Oracle: Flip & Resonance** is a mobile ritual interface for externalizing uncertainty and observing one's own reaction.

It is:

- not a therapist;
- not a fortune teller;
- not a predictor;
- not a diagnostic tool;
- not an AI decision maker.

### Core definition

> **A ritual interface for externalizing uncertainty and observing one's own reaction.**

The Oracle does not claim to know the truth.

> **Oracle doesn't know. That's the point.**

The user formulates a question, mentally or explicitly, and performs a simple gesture to obtain one of three states:

- **YES**
- **NO**
- **UNDEFINED**

The answer is generated randomly and independently of the question.

The important event is what happens **after** the answer.

## 2. Core Principle

When two competing tendencies are close to equilibrium:

$$
A \approx B
$$

the system may remain in a state of unresolved tension.

The Oracle introduces a minimal external perturbation:

$$
A \approx B \rightarrow \Delta \rightarrow Reaction
$$

The random answer does not solve the problem. It breaks the symmetry.

If the Oracle says **YES** and the user immediately feels:

> "No. I don't want that."

then the Oracle has not made a mistake.

It has exposed a previously implicit preference.

## 3. Oracle as Decision Perturbator

The Oracle is not a decision maker.

**Oracle = Decision Perturbator**

Its function is to introduce the smallest possible external difference into an unresolved internal situation.

The Oracle does not provide arguments, facts, probabilities, or authority.

It simply produces:

$$
YES \quad|\quad NO \quad|\quad UNDEFINED
$$

This is a deliberately minimal perturbation.

> **Minimal external difference allows an internal system to reveal its own difference.**

The Oracle therefore performs:

$$
Internal\ Conflict
\rightarrow

\rightarrow

\rightarrow

## 4. The Four Mechanisms

### 4.1 Delegated Uncertainty

The user temporarily delegates the **moment of selection** to an external random mechanism.

The decision itself is never delegated.

The distinction is essential:

> The Oracle chooses the perturbation. The user chooses what to do with it.

### 4.2 Frustration Break

A nearly symmetrical internal state can persist because competing tendencies cancel each other.

The Oracle breaks that symmetry without supplying a competing argument.

$$
A \approx B
\rightarrow
Oracle
\rightarrow
A \neq B
$$

The reaction becomes observable.

### 4.3 Resonance

A single reaction is an event.

Repeated reactions create a pattern.

The system therefore becomes more interesting over time:

$$
Event \rightarrow Pattern \rightarrow Resonance
$$

### 4.4 Memory

Memory is optional.

Free Oracle forgets.

Premium remembers **only because the user explicitly allows it to remember**.

> **Memory by Consent.**

# 12. Dynamic Tension

Dynamic tension is a central analytical concept.

The system should distinguish two independent channels:

$$
T = (T_p,T_m)
$$

where:

- $T_p$ = physical dynamic tension;
- $T_m$ = mental/behavioral dynamic tension.

Important:

$$
Tension \neq Frustration
$$

The application does **not** directly measure frustration, emotion, thought, or psychological state.

It observes measurable proxies.

---

# 13. Physical Dynamic Tension

The phone can observe physical changes following an Oracle response.

Potential features:

- reaction latency;
- orientation delta;
- angular velocity;
- acceleration;
- micro-movements;
- movement energy;
- reaction duration;
- stabilization time;
- latency to the next interaction.

A conceptual model:

$$
T_p = f(\Delta O,V,A,M,D,S)
$$

where the variables represent observable device-derived features.

The application must not say:

> "You were afraid."

It may say:

> "Your physical reaction was stronger than your usual baseline."

The distinction is essential.

---

# 14. Mental / Behavioral Dynamic Tension

The application cannot read thoughts.

It can observe changes in interaction dynamics.

Potential signals:

- number of Oracle sessions;
- sessions per period;
- change relative to baseline;
- length of sequences;
- recursive returns;
- repeated questioning;
- time between related sessions.

A simple frequency measure:

$$
F = \frac{N}{\Delta t}
$$

and change relative to baseline:

$$
\Delta F = F_{current} - F_{baseline}
$$

Example:

Typical behavior:

> 3 sessions per week

Observed behavior:

> 12 sessions in two days

The application should describe this as a **change in interaction pattern**, not as a diagnosis.

A useful technical term is:

> **Mental Activity Signal / Cognitive Recurrence**

"Dynamic mental tension" remains the theoretical interpretation.

# 37. Telegram Oracle

Telegram can serve as a lightweight, fully functional Oracle interface and as an MVP channel for validating the core interaction model.

The Telegram version should not simply be a reduced copy of the mobile application. Its strength is the simplicity of the interaction:

$$
Think \rightarrow FLIP \rightarrow Reveal \rightarrow Reaction
$$

## 37.1 Basic Telegram Interaction

The bot presents:

```text
              ORACLE

       Think of your question.

          ┌─────────────┐
          │    FLIP     │
          └─────────────┘
```

The user does not need to type the question.

When the user presses **FLIP**, Telegram sends the button interaction to the bot.

The bot then generates and reveals:

- YES;
- NO;
- UNDEFINED.

The button press itself is therefore a real Oracle event.

## 37.2 Callback Interaction

The FLIP control should use Telegram's interactive button/callback mechanism.

Conceptually:

```text
User
  │
  │  press FLIP
  ↓
Telegram
  │
  │  callback event
  ↓
Oracle Bot
  │
  │  random response
  ↓
YES / NO / UNDEFINED
```

The bot can edit the original message after the button press rather than sending an unrelated new message.

This allows the ritual to feel like one continuous interaction.

## 37.3 Reveal Sequence

A simple Telegram reveal may use message editing:

```text
FLIP
 ↓
...
 ↓
...
 ↓
YES
```

or:

```text
ORACLE

        FLIP
          ↓
       [ ... ]
          ↓
       [ ... ]
          ↓
          YES
```

The timing and number of intermediate states should remain short enough that the interaction feels responsive.

Telegram cannot reproduce the full physical animation and haptic experience of the native mobile application. Therefore:

> **Telegram is the conversational Oracle. The mobile application is the embodied Oracle.**

## 37.4 Reaction Layer

After revealing the answer, the bot can ask:

```text
YES

What was your reaction?
```

Possible buttons:

```text
[ I liked it ]   [ I didn't ]
[ I don't know ] [ Tell me why ]
```

This creates the second half of the Oracle model.

The Oracle provides the first answer.

The user's reaction provides the second.

$$
Oracle\ Answer \rightarrow Reaction
$$

The optional **Tell me why** action allows the user to voluntarily describe the reaction.

Example:

```text
ORACLE

YES

What was your reaction?

[ I liked it ]
[ I didn't ]
[ I don't know ]
[ Tell me why ]
```

User:

> "I was hoping for NO."

The Oracle has then revealed a possible internal preference without ever claiming to know it beforehand.
